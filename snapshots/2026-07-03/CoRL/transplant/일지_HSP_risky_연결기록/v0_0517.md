# v0 2026-05-17 HSP-Risky 연결 상태 기록

## 요약

현재 transplant 코드는 **HSP env를 Risky에 맞추는 방식**이 아니라, **Risky env 위에서 HSP algorithm / HSP training pipeline만 실행하는 방식**으로 정리되어 있다.

Risky 환경의 실제 MDP, state transition, reward, slip/risked/handoff 판정, event 이름은 `/home/isl_jhoh/CoRL/risky`가 source of truth다. HSP repo에서는 policy pool, runner, trainer, policy, buffer, population loop 같은 학습 알고리즘 구현만 재사용한다.

Hidden utility와 로그/분석 feature는 HSP env의 shaped-info 이름을 쓰지 않고, Risky 원본 `EVENT_TYPES` 순서를 그대로 따른다. 현재 Risky `EVENT_TYPES`는 38개이며, HSP hidden utility weight는 `38 + sparse reward 1 = 39`개 값을 사용한다.

## 배경

처음 transplant adapter는 Risky event를 HSP env의 shaped-info 이름으로 번역하려고 했다. 예를 들면 다음과 같은 매핑이 있었다.

```python
"onion_pickup": ("pickup_onion_from_O",)
"useful_onion_pickup": ("pickup_onion_from_O",)
```

이 방식은 문제가 있었다. Risky에서는 `onion_pickup`과 `useful_onion_pickup`이 서로 다른 event인데, HSP category 하나로 합쳐지면서 정보가 사라졌다. 더 심하게는 useful pickup이 발생하면 basic event와 useful event가 동시에 true가 되므로, 같은 HSP key에 `+=` 되어 한 번의 행동이 `2.0`처럼 기록될 수 있었다.

또한 HSP env의 `pickup_onion_from_O`, `PLACEMENT_IN_POT`, `USEFUL_DISH_PICKUP` 같은 이름은 Risky env의 event 기준이 아니다. 우리가 말하는 HSP는 HSP env가 아니라 HSP 논문/방법론의 학습 절차이므로, event와 log 기준은 Risky env를 따라야 한다.

그래서 현재 v0에서는 다음 원칙으로 바꿨다.

```text
Risky env = event/source of truth
HSP = algorithm/training pipeline
transplant = Risky env와 HSP algorithm code를 연결하는 호환 계층
```

## 전체 흐름

현재 HSP S1 학습에서 한 step이 처리되는 흐름은 다음과 같다.

1. HSP policy가 agent별 primitive action index를 낸다.
   - 예: `0..5` 범위 action index.

2. `RiskyOvercooked.step()`이 action index를 Risky action으로 변환한다.
   - 위치: `/home/isl_jhoh/CoRL/transplant/adapters/risky_overcooked_env.py`
   - 변환 기준: `Action.INDEX_TO_ACTION`
   - 결과: `(agent_action, other_agent_action)` 형태의 `joint_action`

3. 실제 환경 step은 Risky env가 수행한다.

```python
next_state, sparse_reward, done, info = self.base_env.step(
    joint_action,
    display_phi=self.use_phi,
    get_mdp_info=True,
)
```

4. Risky MDP가 `event_infos`를 만든다.
   - 위치: `/home/isl_jhoh/CoRL/risky/src/risky_overcooked_py/mdp/overcooked_mdp.py`
   - 기준: Risky `EVENT_TYPES`
   - 예: `dish_risked`, `onion_pickup`, `useful_onion_pickup`, `soup_handoff`

5. transplant adapter가 `event_infos`를 Risky event vector로 변환한다.

```python
CATEGORY_KEYS = tuple(EVENT_TYPES)
HIDDEN_UTILITY_KEYS = CATEGORY_KEYS
```

즉 별도 HSP 이름으로 번역하지 않고, Risky event 이름과 순서를 그대로 쓴다.

6. step별 event vector는 다음 info key로 제공된다.

```python
info["step_shaped_info_by_agent"]
info["vec_shaped_info_by_agent"]
info["risky_event_infos"]
info["risky_event_counts"]
```

7. episode가 끝나면 누적 event vector가 episode info에 들어간다.

```python
info["episode"]["ep_category_r_by_agent"]
```

현재 shape는 다음과 같다.

```text
vec_shaped_info_by_agent: (2, 38)
ep_category_r_by_agent:  (2, 38)
```

8. `use_hsp=True`이면 hidden utility reward를 계산한다.

```python
hidden_reward = dot(w[:-1], risky_event_vector) + sparse_reward * w[-1]
```

따라서 weight 길이는 다음과 같다.

```text
len(EVENT_TYPES) + 1 = 38 + 1 = 39
```

## 결정 사항

### 결정 1. HSP env shaped-info 이름을 버리고 Risky `EVENT_TYPES`를 기준으로 삼는다.

이 결정이 가장 중요하다.

HSP env shaped-info 이름을 쓰면 Risky에서 서로 다른 event가 하나의 HSP category로 합쳐진다. 특히 `onion_pickup`과 `useful_onion_pickup`처럼 동시에 true가 될 수 있는 event가 같은 key에 누적되면, 실제 한 번의 event가 `2.0`처럼 왜곡될 수 있다.

Risky 실험에서 분석해야 하는 것은 Risky 환경에서 발생한 행동과 사건이다. 따라서 hidden utility, log, analysis는 Risky env가 직접 제공하는 `EVENT_TYPES`를 기준으로 해야 한다. 이 기준을 택하면 event 이름, vector index, weight index, log key가 모두 1:1로 맞는다.

### 결정 2. HSP는 env가 아니라 algorithm / training pipeline만 재사용한다.

우리가 말하는 HSP는 HSP repo의 원본 Overcooked env가 아니다. HSP 논문/방법론의 policy pool 학습 절차다.

그래서 HSP repo에서 재사용할 것은 runner, trainer, policy, buffer, policy pool 같은 학습 코드이고, HSP env의 MDP나 shaped-info 의미 체계는 가져오지 않는다. 이 구분을 하지 않으면 HSP env의 이름과 Risky event 이름이 섞이면서 코드 의미가 틀어진다.

### 결정 3. `RiskyOvercookedRunner`를 transplant에 둔다.

HSP shared runner에는 Overcooked 전용 logging과 조건문이 남아 있다. 원본 HSP runner를 직접 수정하면 HSP repo를 건드리게 되고, 다른 실험에 영향을 줄 수 있다.

그래서 transplant에 `RiskyOvercookedRunner`를 새로 두고, HSP shared runner를 상속하되 Risky event 이름으로 로그를 남기도록 했다. 내부적으로 일부 inherited bookkeeping 때문에 runner field `env_name`을 `"Overcooked"`로 유지하는 부분이 있지만, 이것은 HSP env를 쓴다는 뜻이 아니라 HSP runner의 기존 조건문을 통과시키기 위한 호환 처리다.

### 결정 4. `predict_other_shaped_info`는 우선 비활성화한다.

HSP algorithm code에는 Overcooked shaped-info를 예측하는 보조 과제가 있다. 이 기능은 내부적으로 12차원 등 HSP env 기준 hardcode가 남아 있다.

현재 목표는 Risky env 위에서 HSP training pipeline을 안정적으로 돌리는 것이므로, 이 보조 과제는 `normalize_risky_args()`에서 꺼지도록 했다. 나중에 정말 필요하면 Risky `EVENT_TYPES` 38차원 기준으로 actor head, buffer, trainer_pool까지 별도 확장해야 한다.

## 추가 연결 기록: HSP stage pipeline과 Risky event selection

### 요약

HSP-Risky 이식에서 현재 사용하는 전체 실행 흐름은 MEP S1 후보 생성, HSP S1 biased pair 생성, HSP S1 event 평가, greedy selection, HSP S2 adaptive 학습 순서다.

Risky env의 MDP, event, reward 통계는 원본 `/home/isl_jhoh/CoRL/risky`를 기준으로 유지하고, HSP algorithm code가 기대하는 실행 인자와 policy pool 구조는 `transplant` 계층에서 맞춘다.

특히 HSP S1 event 평가와 greedy selection은 최종 성능 평가가 아니라, HSP S2에 넣을 다양한 biased partner 후보를 고르는 중간 절차다.

### 전체 흐름

1. `01_train_mep_s1_risky.sh`
   - MEP Stage 1 후보 policy pool을 학습한다.
   - HSP 원본 Stage 1 방식에 맞춰 `n_rollout_threads == train_env_batch`가 되도록 한다.
   - 현재 정식 기본값은 `N_ROLLOUT_THREADS=100`, `--train_env_batch "${N_ROLLOUT_THREADS}"` 구조다.

2. `03_train_hsp_s1_risky.sh`
   - HSP S1 biased pair를 seed별로 학습한다.
   - 각 seed는 `w0`, `w1` 두 policy를 pair로 만든다.
   - `w0`는 Risky event hidden utility weight를 가진 biased policy이고, `w1`는 hidden utility event weight가 0인 일반 협력 기준 policy다.
   - HSP 원본 HSP S1 경로처럼 `--train_env_batch`를 별도로 넘기지 않는다.

3. `04_extract_hsp_s1_risky.py`
   - HSP S1 학습 결과에서 actor checkpoint를 추출한다.
   - 추출 결과는 `policy_pool/risky_multipath/hsp/s1/hsp{seed}_w0_actor.pt`, `hsp{seed}_w1_actor.pt` 형태가 된다.
   - 현재 기본 `SEED_MAX=36` 기준으로 `hsp1`부터 `hsp36`까지 후보 pair를 만들 수 있다.

4. `05_eval_events_risky.sh`
   - 각 seed마다 `hsp{seed}_w0` vs `hsp{seed}_w1`, 그리고 `hsp{seed}_w1` vs `hsp{seed}_w0`를 모두 평가한다.
   - 두 방향을 모두 보는 이유는 `w0`가 agent0 slot에 있을 때와 agent1 slot에 있을 때의 Risky event feature를 모두 확보하기 위해서다.
   - 이 단계의 목적은 reward 성능 순위를 매기는 것이 아니라 greedy selection에 넣을 event feature vector를 만드는 것이다.

5. `06_greedy_select_risky.py`
   - `transplant/biased_eval/<layout>/eval_hsp*.txt`에 저장된 raw metric dict를 읽는다.

### HSP S1 event 평가와 greedy selection 인터페이스

`05_eval_events_risky.sh`는 터미널에는 짧은 `eval summary`만 출력하고, greedy selection에 필요한 raw metric dict는 `--metrics_output_path`를 통해 파일에 남긴다.

예시 저장 위치:

```text
transplant/biased_eval/risky_multipath/eval_hsp1.txt
transplant/biased_eval/risky_multipath/eval_hsp2.txt
...
```

`06_greedy_select_risky.py`는 이 파일들에서 다음 형태의 key를 읽는다.

```text
hsp{seed}_w0-hsp{seed}_w1-eval_ep_{event_name}_by_agent0
hsp{seed}_w1-hsp{seed}_w0-eval_ep_{event_name}_by_agent1
```

첫 번째 경우에는 `w0`가 agent0이므로 agent0 event만 사용하고, 두 번째 경우에는 `w0`가 agent1이므로 agent1 event만 사용한다.

이 방식으로 slot 위치에 따른 차이를 줄이고, 각 seed의 biased policy `w0`가 실제로 어떤 Risky event 성향을 보였는지 feature vector로 만든다.

### 주의 사항: eval episode 수와 eval rollout thread 수

HSP shared runner의 multi-policy evaluation은 내부적으로 다음 구조를 사용한다.

```python
for episode in range(num_eval_episodes // self.n_eval_rollout_threads):
```

따라서 `EVAL_EPISODES < N_EVAL_ROLLOUT_THREADS`이면 실제 eval episode가 0번 실행된다.

예를 들어 다음 실행은 문제가 된다.

```bash
EVAL_EPISODES=1 CUDA_VISIBLE_DEVICES=3 bash transplant/scripts/05_eval_events_risky.sh
```

현재 `common.sh` 기본 `N_EVAL_ROLLOUT_THREADS=4`이므로 `1 // 4 = 0`이 되어 raw metric dict가 `{}`로 저장된다.

이 경우 `06_greedy_select_risky.py`는 event feature를 찾지 못하고 다음 fallback으로 이동한다.

```text
warning: no event logs found; selecting first available HSP S1 runs
selected runs: [1, 2, ..., 18]
```

이 출력은 greedy diversity selection이 성공했다는 뜻이 아니라, event log가 비어서 첫 18개를 임시로 고른 것이다.

빠른 확인용으로는 다음처럼 실행한다.

```bash
N_EVAL_ROLLOUT_THREADS=1 EVAL_EPISODES=1 CUDA_VISIBLE_DEVICES=3 bash transplant/scripts/05_eval_events_risky.sh
```

기본 eval thread 4개를 유지하려면 최소한 다음처럼 실행한다.

```bash
EVAL_EPISODES=4 CUDA_VISIBLE_DEVICES=3 bash transplant/scripts/05_eval_events_risky.sh
```

selection 품질을 보려면 `EVAL_EPISODES`를 더 크게 잡는 것이 좋다.

### 남은 수정 포인트

- `05_eval_events_risky.sh`에서 `EVAL_EPISODES < N_EVAL_ROLLOUT_THREADS`일 때 명확히 실패시키는 guard를 추가할지 검토한다.
- 또는 event 평가 스크립트에 한해 기본 `N_EVAL_ROLLOUT_THREADS=1`을 사용할지 검토한다.
- `06_greedy_select_risky.py`의 fallback은 편의상 유지할 수 있지만, fallback이 발생했을 때 사용자가 실제 greedy selection 결과로 착각하지 않도록 경고를 더 강하게 만드는 방안도 고려한다.
