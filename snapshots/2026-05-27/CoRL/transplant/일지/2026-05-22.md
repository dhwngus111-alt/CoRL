## HSP S1 time_cost 분리

### 배경

HSP S1 full run에서 agent0 reward가 비정상적으로 크게 튀는 현상을 확인했다.

원인은 Risky env가 반환하는 timestep scalar `sparse_reward` 안에 `time_cost`가 이미 포함되어 있는데, HSP branch에서 이를 그대로 sparse hidden utility weight와 곱하고 있었기 때문이다.

기존 구조:

```python
hidden_reward = dot(hidden_events, w[:-1]) + sparse_reward * w[-1]
```

이 구조에서는 `w0[-1] == 0`으로 샘플링된 agent0가 delivery sparse reward뿐 아니라 `time_cost`까지 같이 무시하게 된다. seed 1 확인 결과 `w0` sparse weight가 `0`, `w1` sparse weight가 `1`이었고, 이 때문에 agent0가 매 step time penalty를 받지 않는 문제가 생길 수 있었다.

### 수정 내용

`transplant/adapters/risky_overcooked_env.py`의 HSP reward branch에서 `time_cost`를 sparse hidden utility selection과 분리했다.

수정 후 구조:

```python
task_sparse_reward = float(sparse_reward) - self.time_cost

hidden_reward = (
    dot(hidden_events, w[:-1])
    + task_sparse_reward * w[-1]
    + self.time_cost
)
```

의미:

- `time_cost`는 매 env step마다 각 agent reward에 한 번씩 직접 적용된다.
- `w0[-1]` / `w1[-1]` sparse hidden utility weight는 `time_cost`를 제외한 task sparse reward에만 적용된다.
- `use_phi` branch와 non-HSP branch는 변경하지 않았다.
- hidden utility schema, `w0/w1` weight spec, W&B hidden utility selection logging은 변경하지 않았다.
- `dropped_reward_by_agent`는 기존처럼 task sparse reward 쪽에 남긴다.

### 수정 및 반영 사항

1. **학습 규모 변경 (12개 학습 / 6개 추출)**
   - `transplant/common.sh`의 `MEP_POPULATION_SIZE`를 `12`로 변경하여 Stage 1 학습 인구를 12개로 늘렸다.
   - `transplant/build_policy_configs.py`의 기본값을 `12`로 수정하여 `train.yml`에 `mep1`~`mep12`가 포함되도록 정의했다.
   - `00_check_env.sh` 및 `03_train_hsp_s1_risky.sh`에서 `build_policy_configs` 호출 시 `--mep-population-size "${MEP_POPULATION_SIZE}"`를 명시적으로 인자로 주어, 어떤 스크립트 실행 순서에서도 MEP 인구수 설정이 덮어쓰여 롤백되는 오류를 사전 차단했다.
   - 최종 추출 단계(`02_extract_mep_s1_risky.py`)의 `--max-policies`는 기존 **`6`**을 유지하여, HSP S2 및 다운스트림 파이프라인의 최종 MEP 정책 개수(18개 = 6개 모델 * 3체크포인트) 아키텍처 호환성을 완벽하게 지켰다.

2. **W&B `ep_sparse_r` 로깅 상태 검증 및 확정**
   - Overcooked RL의 에피소드 sparse reward 합계 메트릭인 `ep_sparse_r`이 Runner(`separated/overcooked_runner.py` 및 `shared/overcooked_runner.py`) 코드에서 정상적으로 수집되어 W&B로 누락 없이 로깅되고 있음을 코드로 확인했다.
   - 사용자 피드백을 반영하여, 수프 제출(delivery) 횟수 환산(나누기 20 등) 대신 **`ep_sparse_r` 원본 점수 그 자체가 직접 로깅**되도록 확정하여 가시성을 유지했다.

### W&B 세팅 확인용 최소 스텝 테스트 구동

W&B 연동과 `ep_sparse_r` 로깅을 신속히 확인하기 위해 GPU 0번에서 초고속 검증 테스트를 임시 구동했다.

```bash

TIME_COST=0.1 \
USE_WANDB=1 \
bash transplant/scripts/01_train_mep_s1_risky.sh
```

- **W&B 연동**: `dhwngus41` 계정으로 성공적으로 동기화되어 `lyxvhrrs` 런 정보가 실시간 전송되기 시작함을 확인했다.
- **수학적 스텝 매칭 검증 (`NUM_ENV_STEPS` 해석)**:
  - MEP Stage 1에서는 인구 크기(12)배 만큼 `num_env_steps`가 내부적으로 확장된다. (`80,000 * 12 = 960,000` 스텝)
  - `960,000 스텝 // (400 Horizon * 100 threads) = 총 24 에피소드` 루프가 돌게 된다.
  - 에피소드마다 12개 정책이 Round-Robin 형태로 한 번씩 선택되어 학습하므로, 각 개별 MEP 모델은 정확하게 `24 // 12 = 2` 에피소드만큼 학습하게 된다.
  - 이는 개별 모델의 입장에서 `2 에피소드 * 400 Horizon * 100 threads = 80,000` 스텝 학습을 완벽하게 보장한다.
  - **결론**: 사용자가 지정한 `NUM_ENV_STEPS`는 **"각 개별 MEP 에이전트(모델)가 전용으로 분배받는 학습 스텝 크기"**와 수학적으로 1:1 일치한다.
