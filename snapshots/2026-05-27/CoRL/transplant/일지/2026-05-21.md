## MEP Stage 1 W&B local step 정리

### 배경

- MEP Stage 1은 HSP 원본 방식처럼 `mep1..mep6` population을 하나의 run에서 round-robin으로 학습한다.
- 학습 자체는 각 policy가 10M env step씩 받는 구조가 맞다.
- 하지만 기존 W&B x축은 global population step이었다.
  - 예: W&B x축 `7M`은 특정 `mep4`만 7M을 학습했다는 뜻이 아니라 population 전체 진행량이었다.
- 사용자가 원하는 기준은 각 policy 패널이 자기 policy의 local step 기준으로 찍히는 것이다.

### 결정

- 학습 방식은 HSP 원본 MEP Stage 1 구조를 유지한다.
- W&B logging만 수정한다.
- 각 MEP policy metric은 해당 policy의 local step을 x축으로 사용한다.

### 변경 내용

- `transplant/runners/risky_overcooked_runner.py`
  - Stage 1 MEP logging에서 `mepX-total_num_steps`를 읽어 `mepX-local_env_step`을 계산하도록 수정.
  - W&B `define_metric`을 사용해 다음 metric들이 자기 local step을 x축으로 쓰도록 설정.

```text

stage1_mep/train/mep1-value_loss
stage1_mep/train/mep1-policy_loss
stage1_mep/train/mep1-average_episode_rewards
```

### 주의

- 이미 실행 중이던 기존 `full` run에는 코드 수정이 적용되지 않는다.
- final 기록용 MEP W&B는 수정 후 새로 시작한 run을 기준으로 봐야 한다.

## HSP-Risky Overcooked Hidden Utility Schema 및 Weight Spec 최종 정리

### 배경

- `transplant`의 초기 HSP S1 hidden utility default는 HSP core 21개 전체에 `r5`를 적용하는 형태였다.
- 하지만 원본 HSP S1 script들은 `r5` blanket sampling이 아니라 layout별 discrete mask를 사용한다.
- Risky multipath에서는 HSP 원본 core schema를 유지하면서, multipath에서만 새로 의미가 생기는 event를 뒤에 append하기로 했다.
- Slip event는 agent의 명시적 preference라기보다 stochastic outcome에 가까우므로 hidden utility selection 대상에서 제외하기로 했다.

### 최종 결정 및 반영 사항

1. **HSP core 21개 category 유지**
   - 원본 HSP `overcooked_new`의 hidden utility core category 순서를 유지한다.
   - Risky raw potting quality event는 HSP category로 aggregate한다.
   - `optimal_onion_potting`, `optimal_tomato_potting` -> `optimal_placement`
   - `viable_onion_potting`, `viable_tomato_potting` -> `viable_placement`
   - `catastrophic_onion_potting`, `catastrophic_tomato_potting` -> `catastrophic_placement`
   - `useless_onion_potting`, `useless_tomato_potting` -> `useless_placement`

2. **Risky multipath hidden utility event는 8개만 append**
   - Risk path 선택 자체를 나타내는 `*_risked` 4개를 추가한다.
   - 협업 방식 preference를 나타내는 `*_handoff` 4개를 추가한다.
   - Slip event 5개는 hidden utility schema에서 완전히 제외한다.

3. **HSP many_orders core mask를 default로 사용**
   - 기존 core 21개는 HSP repo의 `many_orders.sh` w0 mask를 따른다.
   - Risky 추가 8개는 `r[-5:5:3]`을 사용한다.
   - sparse weight는 HSP many_orders처럼 `r[0:1:2]`을 사용한다.
   - `w1`은 baseline으로 hidden utility 전부 `0`, sparse `1`을 사용한다.

## 학습 시와 평가/테스트(eval/test) 시의 time_cost 격리 설정

### 배경
- **학습(Training) 시**: 에이전트들이 불필요한 대기를 줄이고 빠르게 타스크를 완수하도록 다그치기 위해 `TIME_COST` 페널티(예: `-0.3`)를 부여하여 움직임을 촉진한다.
- **평가 및 테스트(Evaluation & Testing) 시**: 환경 본연의 순수한 sparse reward(soup delivery) 및 behavior event 빈도를 왜곡 없이 측정하기 위해 인위적인 step penalty인 `time_cost`가 개입되지 않고 `0.0`으로 작용해야 한다.
- **문제점**: 기존에는 사용자가 학습 중인 터미널 세션(`export TIME_COST=-0.3`)에서 그대로 평가 스크립트를 실행할 경우, `common.sh`가 환경 변수를 상속받아 평가 시에도 `--time_cost -0.3`이 주입되는 현상이 발생했다.

### 최종 결정 및 반영 사항
- 평가 및 테스트가 실행되는 쉘 스크립트 내부에서, `common.sh`를 로드하기 전 명시적으로 `export TIME_COST=0.0`을 선언하여 환경 오염을 완벽히 격리했다.
- 이로써 어떠한 터미널 세션 환경에서든 평가 스크립트를 구동할 때 강제적으로 `--time_cost 0.0`이 주입되어 순수 평가 지표를 획득할 수 있게 보장했다.

```bash
bash transplant/scripts/03_train_hsp_s1_risky.sh
```

해석:

- `SEED_MAX=36`이므로 seed 1부터 seed 36까지 순차적으로 HSP S1 pair를 학습한다.
- 각 seed에는 `w0` biased policy와 `w1` baseline policy가 pair로 들어간다.
- `NUM_ENV_STEPS=10000000`은 각 seed pair의 environment interaction budget이다.
- 따라서 `w0`와 `w1`은 같은 10M rollout budget 안에서 동시에 학습된다.
- `w0`만 따로 10M, `w1`만 따로 10M을 더해 총 20M으로 세는 구조는 아니다.

### W&B sparse reward metric 해석

HSP S1 W&B에는 다음 sparse reward metric이 올라간다.

```text
seedXX/env/ep_sparse_r
seedXX/env/ep_sparse_r_by_agent0
seedXX/env/ep_sparse_r_by_agent1
```

의미:

- `seedXX/env/ep_sparse_r`는 episode 전체 sparse reward 합이다.
- `seedXX/env/ep_sparse_r_by_agent0`와 `seedXX/env/ep_sparse_r_by_agent1`은 sparse delivery credit이 어느 agent에 붙었는지 보는 attribution metric이다.
- Risky env에서는 soup delivery를 실제 수행한 `player_idx` 쪽에 sparse reward가 누적된다.
- 따라서 보통 `ep_sparse_r = ep_sparse_r_by_agent0 + ep_sparse_r_by_agent1`로 해석한다.
- HSP S1 학습 reward 계산에는 timestep scalar `sparse_reward`가 양쪽 policy reward 계산에 들어가지만, logging에서는 agent별 delivery credit도 따로 남긴다.

예시:

```text
agent0이 soup 2번 delivery, agent1이 0번 delivery:
ep_sparse_r_by_agent0 = 40
ep_sparse_r_by_agent1 = 0
ep_sparse_r = 40

agent0과 agent1이 각각 1번 delivery:
ep_sparse_r_by_agent0 = 20
ep_sparse_r_by_agent1 = 20
ep_sparse_r = 40
```

기본 성능 추세는 `seedXX/env/ep_sparse_r`를 보고, 역할 편향이나 delivery attribution은 `*_by_agent0/1`을 함께 본다.

### 실행/삭제 권한 관련 메모

- Codex는 사용자가 명시적으로 요청하기 전에는 학습 실행을 하지 않는다.
- Codex는 사용자가 명시적으로 요청하기 전에는 결과 디렉터리 삭제도 하지 않는다.
- 실행 코드 제시는 가능하지만, 실제 `bash transplant/scripts/03_train_hsp_s1_risky.sh` 실행은 사용자가 직접 수행한다.

확인 시점의 filesystem 상태:

```text
2026-05-21 20:42-20:45 기준으로 다음 산출물이 다시 생성되어 있었다.

transplant/results/RiskyOvercooked/risky_multipath/mappo/hsp-S1/run1
transplant/results/RiskyOvercooked/risky_multipath/mappo/hsp-S1/wandb/run-20260521_204226-r1hgtp0z
transplant/policy_pool/risky_multipath/policy_config
```

같은 시점에 활성 HSP S1 학습 프로세스는 확인되지 않았다.
