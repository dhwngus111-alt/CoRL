## 1. antigravity (설계 및 운영 결정)

### 어떤 과정을 진행했는가

- HSP pipeline에서 `risky_overcooked` 보상 설정이 MEP 학습에 제대로 반영되는지 확인했다.
- 중요한 범위를 다음과 같이 분리했다.
  - HSP S1에서 policy pool에 들어가는 HSP policy 학습 과정은 건드리지 않는다.
  - HSP S1 이전에 수행되는 MEP policy 학습 과정만 reward shaping 설정을 수정한다.
- 확인 결과 `handoff_shaping`만 MEP S1에서 켜야 하는 누락 설정으로 판단했다.
- `old_reward_shaping`, `shared_reward_split`, `neglect_boarders`는 유지하기로 결정했다.
  - `old_reward_shaping=False`: old shaping이 꺼진 것이 아니라 새 handoff-aware distance shaping 경로를 쓰는 상태이다.
  - `shared_reward_split=False`: 공동 기여 reward를 나누지 않고 기여자에게 full credit을 주는 설정이다. MEP 협업 유도 목적에는 유지가 맞다.
  - `neglect_boarders=False`: reward switch가 아니라 특정 border counter 사용 제한 옵션이다.
- MEP S1 학습에서 사용할 주요 dynamics/reward 기본값을 다시 확인했다.
  - `time_cost=-0.3`
  - `episode_length=200`
  - `p_slip=0.4`
  - `subgoal_disable_steps=60`
  - `num_env_steps=10000000`
  - `n_rollout_threads=100`
  - `handoff_shaping=1` for MEP S1

### 왜 그 과정이 필요한가

MEP가 협업을 잘 못하는 문제를 보상 shaping 관점에서 다시 확인했다. HSP policy 자체의 학습 보상을 바꾸면 기존 HSP S1 후보 pool의 의미가 바뀔 수 있으므로, 이번에는 MEP Stage 1 학습에 한정해 `handoff_shaping`을 켜는 방향으로 정리했다.

또한 `risky_overcooked` layout 파일의 `p_slip` 값과 transplant 실행 CLI의 `p_slip` 값이 일부 layout에서 달랐다. 실제 학습에서는 CLI 값이 MDP kwargs로 덮어써지므로 `0.4`가 적용되지만, source layout 파일 값이 다르면 이후 재현과 검토에서 혼란이 생길 수 있어 layout 파일도 `0.4`로 맞췄다.

### 기존 환경인 HSP에서는 어떤 것을 사용하거나 수정했는가

- HSP algorithm code 자체는 수정하지 않았다.
- HSP S1에서 HSP policy pool에 들어가는 HSP policy 학습 과정도 수정하지 않았다.
- transplant wrapper에서 MEP S1을 실행할 때만 `handoff_shaping`이 기본으로 켜지도록 했다.

### 기존 환경인 risky에서는 어떤 것을 사용하거나 수정했는가

- Risky source of truth layout으로 다음 subgoal layout들을 확인했다.
  - `risky_dualpath_subgoal`
  - `risky_multipath_subgoal`
  - `risky_mixed_coordination_subgoal`
- `risky_overcooked` reward path를 확인했다.
  - delivery sparse reward와 `time_cost`는 base env sparse reward에 포함된다.
  - `PLACEMENT_IN_POT_REW`, `DISH_PICKUP_REWARD`, `SOUP_PICKUP_REWARD`, `DISTANCE_SHAPING_REW`, `SUBGOAL_PRESS_REW`는 dense shaped reward에 포함된다.
  - `handoff_shaping=True`일 때 object-centric handoff-aware distance shaping을 사용한다.
  - drop reward 관련 key는 보이지만 실제 drop reward 값은 현재 구현에서 zero로 쓰인다.
- `p_slip` source layout 값을 `0.4`로 정렬했다.
  - `risky_multipath_subgoal.layout`: `0.15 -> 0.4`
  - `risky_mixed_coordination_subgoal.layout`: `0.25 -> 0.4`

## 2. codex (구현 및 검증)

### 어떤 과정을 진행했는가

- `transplant/scripts/01_train_mep_s1_risky.sh`에서 MEP S1에 한정해 `handoff_shaping`이 기본 ON이 되도록 수정했다.

```bash
export HANDOFF_SHAPING="${MEP_HANDOFF_SHAPING:-${HANDOFF_SHAPING:-1}}"
```

- `transplant/common.sh`의 공통 기본값은 유지했다.
  - `HANDOFF_SHAPING="${HANDOFF_SHAPING:-0}"`
  - 따라서 HSP S1/HSP S2 쪽은 명시하지 않으면 기존처럼 handoff shaping이 꺼진다.
- `risked_overcooked` layout 파일 두 개를 수정했다.
  - `risked_overcooked/src/risky_overcooked_py/data/layouts/risky_multipath_subgoal.layout`
  - `risked_overcooked/src/risky_overcooked_py/data/layouts/risky_mixed_coordination_subgoal.layout`

### 산출물 위치 정리

- MEP S1 raw checkpoint와 W&B local run:

```text
transplant/results/RiskyOvercooked/<layout>/mep/mep-S1
```

- extract 이후 policy pool:

```text
transplant/policy_pool/<layout>/mep/s1
```

기존 `results`가 남아 있으면 같은 layout/stage에 대해 다시 extract할 수 있다. 다만 같은 `policy_pool/<layout>/mep/s1`로 extract하면 policy pool 파일은 같은 이름으로 갱신될 수 있으므로, 기존 extract 결과를 보존하려면 policy pool 디렉터리를 백업하거나 별도 layout/policy pool 이름을 사용하는 편이 안전하다.

### 남은 주의 사항

- 이번 수정은 MEP S1 reward shaping 보정이 목적이다.
- HSP S1의 HSP policy 학습 과정은 의도적으로 수정하지 않았다.
- `handoff_shaping`은 MEP S1에서 기본 ON이지만, 실행 커맨드에는 `MEP_HANDOFF_SHAPING=1`을 명시해 재현성을 높이는 쪽으로 정리했다.
