# 2026-07-02 일일 업무 일지

## 1. antigravity (설계 및 운영 결정)

### 어떤 과정을 진행했는가

- `GAMMA_transplant`의 VAE 학습 설정을 GAMMA paper Table 2 기준으로 다시 점검했다.
- VAE dataset 구성과 train/valid split 기준을 정리했다.
  - dataset은 `mep1_1`부터 `mep8_3`까지 8개 MEP policy의 init/mid/final checkpoint, 총 24개 policy가 만든 trajectory로 구성된다.
  - HDF5에는 별도 valid group 없이 `train` group에 전체 trajectory가 들어 있다.
  - VAE 학습 시점에 `VAETrainer`가 trajectory row 단위로 `train:valid = 7:3` split을 만든다.
  - 따라서 valid split을 만들기 위해 MEP rollout을 다시 수행할 필요는 없다.
- VAE의 KL penalty schedule을 논문 표기와 맞추는 방향으로 결정했다.
  - `beta: 0 -> 1`
  - 시작값 0, 마지막 epoch에서 1이 되도록 선형 증가한다.
- VAE W&B logging 범위를 정리했다.
  - 기존에는 encoder/decoder의 모든 parameter norm이 `vae_train`에 올라가서 `cnn.*.weight`, `cnn.*.bias` panel이 대량 생성되고 있었다.
  - 해당 값들은 gradient/debug 용도에 가깝고 VAE 성능 해석에는 불필요하므로 제거하기로 결정했다.
  - 최종적으로 `vae_train`에는 성능 확인용 scalar 7개만 남긴다.
- VAE 학습 실행 리소스를 점검했다.
  - layout별로 GPU 하나씩 배정하면 병렬 실행은 가능하다고 판단했다.
  - 단일 VAE process가 GPU memory를 크게 사용할 수 있으므로 같은 GPU에 두 개 이상 올리는 것은 피한다.
- HDF5 dataset을 `/dev/shm`으로 복사해 학습 속도를 높이는 방법을 검토했다.
  - `/home`은 ZFS이고 dataset file은 logical size와 physical disk usage가 크게 다르다.
  - `du -h` 기준으로는 7-9GB처럼 보이지만, apparent/logical size는 75G, 118G, 89G 수준이다.
  - `/dev/shm`은 tmpfs이므로 logical size 기준으로 RAM을 점유할 수 있다.
  - 따라서 현재는 `/dev/shm` 복사 없이 디스크에서 학습하는 쪽이 안전하다고 판단했다.
- GAMMA S2 adaptive policy 학습 전에 W&B run name과 train env metric 범위를 미리 정리했다.
  - run name은 layout이 바로 보이도록 `04_gamma_s2_${LAYOUT}_seed${SEED}` 형식으로 정리했다.
  - train env metric은 team sparse reward와 adaptive policy 기준 reward만 남기기로 했다.

### 왜 그 과정이 필요한가

GAMMA VAE와 S2 adaptive policy는 이후 Risky GAMMA baseline의 핵심 비교 지점이다. 논문 설정, 원본 GAMMA repo 관습, Risky transplant protocol이 섞이면 다음 문제가 생긴다.

- VAE의 KL schedule과 valid split이 논문과 다르면 latent representation 품질을 해석하기 어렵다.
- W&B에 불필요한 parameter-level panel이 쌓이면 실제로 봐야 할 loss/accuracy/KL 변화가 묻힌다.
- dataset split이 policy 단위인지 trajectory 단위인지 혼동하면 valid 성능을 잘못 해석할 수 있다.
- S2 reward logging에서 team reward, adaptive reward, partner reward가 섞이면 adaptive policy가 실제로 개선되는지 판단하기 어렵다.

오늘 정리는 VAE 학습을 바로 돌릴 수 있는 상태로 만들고, 이후 S2 adaptive policy 학습 때 봐야 할 W&B 지표를 미리 좁히기 위한 것이다.

### 기존 환경인 HSP에서는 어떤 것을 사용하거나 수정했는가

- HSP algorithm code와 HSP env는 오늘 작업에서 직접 수정하지 않았다.
- 기존 HSP/Risky transplant에서 만들어 둔 MEP policy pool을 GAMMA source population의 입력으로 사용한다.
- HSP env의 event/shaped-info 이름은 GAMMA VAE dataset이나 GAMMA S2 metric의 기준으로 사용하지 않는다.
- Risky 실험의 source of truth는 계속 Risky env와 transplant adapter이다.

### 기존 환경인 risky에서는 어떤 것을 사용했는가

- GAMMA baseline 대상 layout은 기존 Risky 3개 layout을 그대로 사용한다.
  - `risky_dualpath_subgoal`
  - `risky_mixed_coordination_subgoal`
  - `risky_multipath_subgoal`
- VAE dataset은 Risky env 위에서 MEP source policies를 rollout해 만들어진 HDF5를 사용한다.
- VAE 자체는 reward를 사용하지 않으므로, MEP policy가 handoff shaping으로 학습되었는지 여부는 policy behavior의 출처일 뿐 VAE loss 계산에는 직접 들어가지 않는다.
- 현재 Risky protocol 값은 유지한다.
  - `EPISODE_LENGTH=200`
  - `P_SLIP=0.4`
  - `TIME_COST=-0.3`
  - `SUBGOAL_DISABLE_STEPS=60`

### VAE 학습량 및 진행률 계산

- 세 layout의 dataset row 수는 동일하다.

```text
total rows: 99,648
valid rows: 29,894
train rows: 69,754
vae_batch_size: 64
batches per epoch: ceil(69,754 / 64) = 1,090
vae_epoch: 500
total optimizer steps: 1,090 * 500 = 545,000
```

- W&B의 `Step`은 environment step이 아니라 VAE optimizer update step이다.
- 예를 들어 W&B step이 약 30,000이면 전체의 약 5.5%이며, 대략 epoch 27-28 수준이다.

### 주의 사항

- `mixed` VAE run은 parameter-level W&B logging 제거 전에 시작한 process이다.
  - 학습 결과 자체는 사용할 수 있다.
  - 다만 W&B panel과 terminal log에는 `encoder_weight/*`, `decoder_weight/*` 노이즈가 계속 남는다.
- `dualpath`, `multipath`는 새 코드로 시작했으므로 새 run 기준 `vae_train` panel은 7개만 올라간다.
- 현재 HDF5에는 별도 `test` group이 없으므로 `vae_heldout_test/*`는 올라가지 않는다.
  - 우리가 말하는 0.3 split은 VAE validation split이다.
  - 앞으로 혼동을 피하기 위해 이 split은 `valid`라고 부른다.
- VAE checkpoint는 encoder/decoder가 따로 저장된다.
  - `encoder_<name>.pt`
  - `decoder_<name>.pt`
  - `encoder.pt`
  - `decoder.pt`
- 현재 `encoder.pt`, `decoder.pt`는 저장 시점마다 덮일 수 있으므로, S2에서 어떤 checkpoint를 사용할지는 이후 정리할 필요가 있다.
