# v2 2026-05-21 MEP Stage 1 full run 구조 정리

## 요약

이번 버전은 Risky 환경 위에서 MEP Stage 1을 최종 baseline partner pool 생성용으로 실행하는 구조를 정리한다.

핵심 변경은 MEP Stage 1을 `6`개 population policy로 학습하고, 이후 각 policy에서 `init/mid/final` checkpoint를 추출해 최종 MEP pool `18`개를 만드는 구조를 명확히 한 것이다.

또한 Risky 환경의 `time_cost`가 transplant 공통 실행 인자로 들어가도록 정리되어, full run에서 `TIME_COST=-0.3`을 shell 환경변수로 제어할 수 있게 되었다.

## 배경

HSP-Risky 이식 pipeline에서 MEP는 HSP S2 adaptive policy가 만날 baseline partner pool의 한 축이다.

따라서 MEP Stage 1은 단순한 smoke run이 아니라, 최종 adaptive policy 평가와 논문 baseline 성능 비교에 들어갈 policy들을 만드는 본 실행이다.

이 과정에서 다음 혼동을 정리할 필요가 있었다.

- `NUM_ENV_STEPS=10000000`이 전체 run 10M인지, 각 MEP policy 10M인지.
- `01_train_mep_s1_risky.sh`만 실행하면 최종 policy pool이 완성되는지.
- `results`와 `policy_pool` 중 어떤 경로가 raw checkpoint이고 어떤 경로가 후속 평가용 pool인지.
- HSP 원본 MEP 설정과 Risky-specific 설정이 어디까지 일치하고 어디서 달라지는지.
- `time_cost`, `p_slip`, `neglect_boarders` 같은 Risky 설정을 어떻게 둘지.

## 전체 흐름

1. `00_check_env.sh`
   - Risky env adapter가 reset/step/render를 정상 수행하는지 확인한다.
   - Risky event vector dim이 현재 `38`인지 확인한다.

2. `01_train_mep_s1_risky.sh`
   - MEP Stage 1 population policy를 학습한다.
   - 현재 full run 기준 population은 `mep1`부터 `mep6`까지다.
   - 각 policy는 `NUM_ENV_STEPS=10000000` budget을 갖는다.
   - 따라서 전체 MEP run의 total timestep은 `6 × 10M = 60M`으로 표시된다.
   - raw checkpoint와 W&B local run은 `results/RiskyOvercooked/risky_multipath/mep/mep-S1` 아래에 저장된다.

3. `02_extract_mep_s1_risky.py`
   - `01`에서 저장된 raw checkpoint를 읽는다.
   - 각 MEP policy에서 `init`, `mid`, `final` checkpoint를 고른다.
   - 최종적으로 `6 × 3 = 18`개 actor `.pt`와 `eval.yml`을 `policy_pool/risky_multipath/mep/s1` 아래에 저장한다.

4. 이후 HSP S2/adaptive 단계
   - 후속 adaptive 학습과 평가에서는 `results`의 raw checkpoint를 직접 쓰기보다 `policy_pool/risky_multipath/mep/s1`의 추출된 policy들을 partner pool로 사용한다.

## 사용하는 것 / 사용하지 않는 것

- HSP algorithm code에서 사용하는 것:
  - MEP Stage 1 학습 구조.
  - population policy 학습 흐름.
  - HSP 논문/repo의 Stage 1 hyperparameter 성격.

- HSP env에서 사용하지 않는 것:
  - HSP Overcooked env의 transition, event schema, shaped-info schema.
  - `neglect_boarders` 같은 Risky observation-specific 옵션은 HSP 원본 설정으로부터 온 것이 아니다.

- Risky env에서 기준으로 삼는 것:
  - `risky_multipath` layout.
  - Risky MDP dynamics.
  - `p_slip=0.15`.
  - `time_cost=-0.3`.
  - Risky `EVENT_TYPES`와 38차원 event vector.

- transplant에서 담당하는 것:
  - HSP algorithm code가 Risky env를 호출할 수 있도록 adapter를 제공한다.
  - shell script에서 HSP-style hyperparameter와 Risky-specific 인자를 함께 넘긴다.
  - raw training result와 final policy pool을 분리한다.
  - W&B logging key를 Stage별로 정리한다.

`transplant/scripts/01_train_mep_s1_risky.sh`의 구조:

2. `transplant.build_policy_configs`를 실행해 `policy_pool/risky_multipath/mep/s1/train.yml`을 만든다.

`transplant/scripts/02_extract_mep_s1_risky.py`의 구조:

1. `results/RiskyOvercooked/risky_multipath/mep/mep-S1` 아래의 MEP checkpoint를 찾는다.
2. `mep1`부터 `mep6`까지 각 policy별 checkpoint를 모은다.
3. `init`, `mid`, `final` checkpoint를 선택한다.
4. `policy_pool/risky_multipath/mep/s1`에 actor `.pt`와 `eval.yml`을 저장한다.

## event / feature / log 기준

- MEP Stage 1의 학습 reward는 hidden utility selection용 event feature가 아니라, Risky 환경 reward와 reward shaping을 통해 계산되는 학습 신호다.
- Risky `EVENT_TYPES`는 HSP hidden utility와 HSP event selection에서 source of truth로 사용한다.
- MEP Stage 1 W&B logging은 현재 핵심 학습 scalar 중심으로 본다.
  - `stage1_mep/train/mepX-value_loss`
  - `stage1_mep/train/mepX-policy_loss`
  - `stage1_mep/train/mepX-average_episode_rewards`
- GIF는 필수 확인 대상이 아니다.
  - MEP full run에서는 우선 reward/loss 추세, NaN/inf 여부, W&B upload 정상 여부를 본다.
  - reward가 장시간 `-120` 근처에 고정되거나 특정 policy만 비정상적으로 다를 때 GIF를 확인한다.

## 결정 사항

### 결정 1: MEP population은 6으로 둔다

현재 transplant full run은 `MEP_POPULATION_SIZE=6`을 사용한다.

이유:

- 후속 pool에서 필요한 MEP partner 수는 `18`개다.
- `02_extract_mep_s1_risky.py`가 각 policy에서 `init/mid/final` 3개를 뽑는다.
- 따라서 `6 × 3 = 18`로 최종 MEP pool 크기와 맞는다.

주의:

- HSP 공개 repo의 MEP Stage 1 script는 raw population size가 `12`인 설정이 있다.
- 따라서 "HSP repo script를 문자 그대로 복제"하는 기준에서는 `6`이 완전 동일하지 않다.
- 하지만 "최종 HSP/adaptive pool에 들어갈 MEP policy 18개" 기준으로는 현재 구조가 명확하고 일관적이다.

### 결정 2: `01`과 `02`는 분리한다

`01_train_mep_s1_risky.sh`는 학습과 raw checkpoint 저장만 담당한다.

`02_extract_mep_s1_risky.py`는 후속 평가용 policy pool을 만드는 별도 단계다.

이유:

- raw checkpoint 저장 위치와 최종 policy pool 위치가 다르다.
- 추출 기준을 바꾸거나 재추출해야 할 수 있으므로 학습과 분리하는 편이 안전하다.
- 학습이 끝난 뒤 policy pool을 명시적으로 확인할 수 있다.

### 결정 3: `time_cost`는 transplant 공통 인자로 넘긴다

Risky env adapter와 parser에는 `time_cost`가 존재하므로, shell 실행에서도 `TIME_COST`로 제어할 수 있어야 한다.

현재 구조:

```bash
export TIME_COST=-0.3
```

`common.sh`가 이를 다음 Python 인자로 변환한다.

```text
--time_cost -0.3
```

이유:

- Risky 환경의 step penalty 성격을 full run에 명확히 반영하기 위해서다.
- `TIME_COST=-0.3`, `EPISODE_LENGTH=400`이면 아무것도 못 했을 때 episode reward가 약 `-120` 근처가 된다.
- 따라서 MEP 초기 reward가 `-119.x` 근처인 것은 정상 초기 상태로 해석한다.

### 결정 4: `neglect_boarders`는 켜지 않는다

현재 full MEP/HSP 이식에서는 `neglect_boarders=False`를 유지한다.

이유:

- HSP 원본 repo에는 `neglect_boarders`에 대응되는 실행 옵션이 없다.
- 이 옵션은 reward가 아니라 observation encoding 영역에 영향을 주는 Risky-specific 설정이다.
- HSP-style baseline과 맞추려면 별도 이유가 없는 한 켜지 않는 편이 자연스럽다.

## 검증 기준

MEP full run 시작 후 확인할 것:

- W&B run 생성:
  - project: `RiskyOvercooked`
  - run name 예시: `01_mep-S1_mep_mep-S1_seed1`
- W&B upload:
  - internal log에 `200 OK`가 반복적으로 나타나야 한다.
- config:
  - `num_env_steps: 10000000`
  - `population_size: 6`
  - `episode_length: 400`
  - `n_rollout_threads: 100`
  - `p_slip: 0.15`
  - `time_cost: -0.3`
- 진행률:
  - total timestep 목표는 `60000000`으로 표시되어야 한다.
  - update당 증가량은 `100 × 400 = 40000` timestep이다.
  - 전체 update 수는 `60000000 / 40000 = 1500`이다.
- 초기 reward:
  - `TIME_COST=-0.3`이면 초반 reward가 `-120` 근처인 것은 자연스럽다.
  - plateau 판단은 너무 이른 시점에서 하지 않는다.
  - 최소 `5M~10M / 60M`, 즉 대략 `updates 125~250` 이후부터 추세를 본다.

## 2026-05-21 추가 기록: W&B logging 구조 정리

### MEP Stage 1 local step logging

MEP Stage 1 학습 구조는 HSP 원본처럼 population 전체를 하나의 run에서 round-robin으로 학습한다.

HSP 원본 runner 기준:

- `trainer_name = self.population[episode % self.population_size]`
- `self.num_env_steps *= self.population_size`

따라서 `NUM_ENV_STEPS=10000000`, `MEP_POPULATION_SIZE=6`이면 terminal/W&B global progress는 `60000000`까지 간다.

다만 W&B에서 `mep1`, `mep2` 등의 패널 x축이 global population step이면 각 policy의 실제 학습 step으로 해석하기 어렵다. 이를 해결하기 위해 Stage 1 MEP logging을 다음 기준으로 정리했다.

```text
stage1_mep/train/mepX-local_env_step
stage1_mep/train/mepX-value_loss
stage1_mep/train/mepX-policy_loss
stage1_mep/train/mepX-average_episode_rewards
```

각 `mepX-*` metric은 `mepX-local_env_step`을 W&B custom x축으로 사용한다.

### HSP Stage 1 single W&B run

기존 HSP S1은 seed마다 Python process를 새로 실행하고, 그때마다 W&B run이 새로 생성되는 구조였다.

변경 후 구조:

- HSP S1 전체에 대해 W&B run 하나만 생성한다.
- 내부에서 seed `1..SEED_MAX`를 순차 학습한다.
- 각 seed의 checkpoint와 `policy_config.pkl`은 기존 extract script가 읽을 수 있도록 local `run1`, `run2`, ... 폴더에 저장한다.

관련 entrypoint:

```text
transplant/train_risky_hsp_s1_bundle.py
```

shell script:

```text
transplant/scripts/03_train_hsp_s1_risky.sh
```

### HSP Stage 1 구조 변경 상세

이번 변경은 단순히 W&B metric 이름만 바꾼 것이 아니라, HSP S1 실행 구조도 일부 정리했다.

최종 실행 흐름:

```text
03_train_hsp_s1_risky.sh
  -> python -m transplant.train_risky_hsp_s1_bundle
      -> W&B run 1개 생성
      -> for seed in 1..SEED_MAX
          -> make_numbered_run_dir()
          -> train_hsp_s1(seed_args, run=bundle_run, local_run_dir=runN)
              -> RiskySeparatedOvercookedRunner
                  -> HSP separated OvercookedRunner.run()
                  -> seedXX/... 형태로 W&B reward metric 기록
                  -> runN/ 아래에 checkpoint 저장
```

파일별 역할:

| 파일 | 구조 변경 | 역할 |
|---|---|---|
| `transplant/scripts/03_train_hsp_s1_risky.sh` | seed loop 제거 | shell에서는 bundle entrypoint를 1번만 호출 |
| `transplant/train_risky_hsp_s1_bundle.py` | 신규 추가 | W&B run 하나를 열고 seed `1..SEED_MAX`를 순차 학습 |
| `transplant/train_risky_hsp.py` | 함수화 | 기존 단일 seed 학습을 `train_hsp_s1()`로 재사용 가능하게 분리 |
| `transplant/common.py` | helper 추가 | `make_results_root()`, `make_numbered_run_dir()`로 W&B run root와 seed별 local run dir 분리 |
| `transplant/runners/risky_overcooked_separated_runner.py` | 신규 추가 | HSP S1 separated runner용 Risky/W&B wrapper |
| `transplant/runners/risky_overcooked_runner.py` | HSP prefix fallback 반영 | shared runner 경로에서도 seed prefix 규칙을 동일하게 맞춤 |
| `HSP/hsp/runner/separated/overcooked_runner.py` | hook 추가 | `_on_train_env_infos()`가 있으면 env info 후처리를 끼울 수 있게 함 |

중요한 구조적 의도:

- HSP S1은 `--share_policy` 인자를 전달하므로 HSP parser 특성상 `share_policy=False`가 되고, separated runner 경로를 탄다.
- W&B run은 bundle에서 1개만 생성한다.
- 각 seed 학습은 독립적으로 새 runner/env/buffer를 만든다.
- 각 seed의 checkpoint는 W&B run dir이 아니라 local `runN` 폴더에 저장한다.
- 따라서 기존 `04_extract_hsp_s1_risky.py`가 기대하는 다음 구조를 유지한다.

```text
transplant/results/RiskyOvercooked/risky_multipath/mappo/hsp-S1/run1
transplant/results/RiskyOvercooked/risky_multipath/mappo/hsp-S1/run2
...
```

checkpoint 예시:

```text
run1/policy_config.pkl
run1/actor_agent0_periodic_*.pt
run1/actor_agent1_periodic_*.pt
```

이 구조 덕분에 W&B에서는 HSP S1이 하나의 run으로 보이고, local filesystem에서는 seed별 결과가 분리되어 extract 단계가 기존 방식대로 동작한다.

```text
per-step hidden utility event count
```

단, seed별로 확정된 `w0/w1` hidden utility selection은 학습 중 변하는 event metric이 아니라 고정 reference 정보이므로 W&B table과 local CSV로 1회 기록하도록 추가했다.

### HSP Stage 1 hidden utility schema 구조 변경

HSP S1 hidden utility schema는 HSP core 21개 category에 Risky multipath event를 append하는 구조다.

최종 schema:

```text
HSP core 21개
+ Risky multipath 8개
= hidden utility 29차원

w0/w1 length = hidden utility 29 + sparse 1 = 30
```

Risky multipath에서 hidden utility selection 대상으로 남긴 event:

```text
tomato_risked
onion_risked
dish_risked
soup_risked
tomato_handoff
onion_handoff
dish_handoff
soup_handoff
```

Hidden utility selection에서 제외한 slip event:

```text
tomato_slip
onion_slip
dish_slip
soup_slip
empty_slip
```

제외 이유:

- `*_risked`는 위험 경로 선택이라는 preference에 직접 대응된다.
- `*_handoff`는 협업 방식 preference에 대응된다.
- `*_slip`과 `empty_slip`은 agent가 선택한 preference라기보다 stochastic outcome에 가까우므로 hidden utility reward feature에서 제외한다.

현재 default weight spec:

```text
w0 = HSP many_orders core 21개 mask + r[-5:5:3] * 8 + r[0:1:2]
w1 = 0 * 29 + 1
```

`r[-5:5:3]`는 연속 난수가 아니라 HSP 원본 방식의 discrete choice이며, seed별로 `{-5, 0, 5}` 중 하나가 선택된다.

W&B/CSV hidden utility selection logging:

- `sample_hsp_weights()` 이후 확정된 숫자형 `w0/w1`을 기록한다.
- W&B key는 `{seed_label}/hidden_utility_selection`이다.
- local CSV는 각 seed local run dir 아래 `hidden_utility_selection.csv`로 저장한다.
- 이 table로 `w0`에는 selection이 반영되고 `w1`은 baseline인지 확인한다.

### reward metric 해석

`train/average_episode_rewards`는 학습 buffer에 실제로 들어간 reward다.

HSP S1에서는 다음 항목이 포함된 학습 reward로 해석한다.

```text
hidden utility event reward
+ sparse reward
+ time_cost
+ reward_shaping_factor * dense_shaping_reward
```

2026-05-22 기준으로 HSP branch에서는 `time_cost`를 sparse hidden utility weight와 분리했다.

```text
task_sparse_reward = scalar_sparse_reward - time_cost

hsp_reward =
  hidden_event_dot
  + task_sparse_reward * sparse_hidden_weight
  + time_cost
```

따라서 `w0/w1`의 sparse hidden weight가 `0`으로 선택되어도 step penalty인 `time_cost`는 매 env step마다 각 agent reward에 남는다.

`env/ep_sparse_r`는 episode 동안 누적된 sparse reward 합이다. 주로 soup delivery 성과를 본다.

`env/ep_sparse_r_by_agent0`와 `env/ep_sparse_r_by_agent1`은 sparse reward가 어느 agent에게 credit 되었는지 보는 attribution metric이다.

Risky env에서는 soup delivery reward가 실제로 delivery를 수행한 `player_idx` 쪽에 누적된다. 따라서 보통 다음 관계로 해석한다.

```text
ep_sparse_r = ep_sparse_r_by_agent0 + ep_sparse_r_by_agent1
```

HSP S1 학습 reward 계산에는 timestep scalar `sparse_reward`가 양쪽 policy reward 계산에 들어가지만, W&B logging에서는 팀 전체 sparse 성과와 agent별 delivery credit을 함께 남긴다.

`env/ep_shaped_r`는 Risky/Overcooked 기본 dense shaping reward 누적이다. 예시는 다음과 같다.

- pot에 양파/토마토 넣기
- 유용한 dish pickup
- soup pickup

`env/ep_shaped_r`는 hidden utility selection reward 자체가 아니다.

`ep`는 episode의 줄임말이다.

### HSP S1 final GIF 생성 시점

HSP S1은 `--share_policy` 인자가 HSP parser에서 `store_false`로 처리되므로 separated runner 경로를 탄다.

따라서 final GIF 생성도 shared runner가 아니라 `RiskySeparatedOvercookedRunner`에서 처리해야 한다.

현재 구조에서는 각 seed policy pair가 `num_env_steps`만큼 학습을 끝낸 직후 final render rollout을 1회 실행한다.

기본 full run 기준:

```text
updates 249/250
total num timesteps 10000000/10000000
-> generated 3/3 final HSP S1 GIFs for seedXX at step 10000000
-> 다음 seed 학습 시작
```

저장 경로:

```text
transplant/results/RiskyOvercooked/risky_multipath/mappo/hsp-S1/runN/gifs/risky_multipath/final_hsp_s1/env_{0..2}/.../*.gif
```

W&B key:

```text
seedXX/final_gifs/step_10000000_gif_1
seedXX/final_gifs/step_10000000_gif_2
seedXX/final_gifs/step_10000000_gif_3
```

### separated runner에서의 render 방식

Shared runner와 달리 HSP S1 separated runner는 agent별 trainer를 가진다.

따라서 final render rollout에서는 각 step마다 다음 방식으로 action을 만든다.

```text
for agent_id in num_agents:
    trainer[agent_id].policy.act(obs[:, agent_id], rnn_states[:, agent_id], masks[:, agent_id])

actions = stack agent actions into (render_threads, num_agents, action_dim)
final_render_envs.step(actions)
```

Risky env adapter는 `use_render=True`인 render env에서 trajectory frame을 기록하고, episode 종료 시 `imageio.mimsave`로 GIF를 저장한다.

### time_cost 비교용 동시 실행의 의미

`time_cost = 0.0, -0.1, -0.2, -0.3` 네 설정을 W&B에서 비교하기 위해 동시에 실행할 수 있다.

W&B run은 내부 run id로 구분되므로 run name 또는 display name이 같아도 logging은 서로 덮어쓰이지 않는다.

하지만 local filesystem에서는 같은 `hsp-S1` root 아래 `runN` directory가 배정된다. 여러 HSP S1 process를 동시에 돌리면 서로 다른 time_cost run의 seed 결과가 local run directory 순서상 섞일 수 있다.

따라서 이 동시 실행 결과는 다음 용도로만 사용한다.

```text
사용 가능:
- W&B reward curve 비교
- hidden utility selection table 확인
- seed별 final_gifs 행동 비교

사용 금지:
- 04_extract_hsp_s1_risky.py로 최종 S2 policy pool 구성
```

최종으로 사용할 `time_cost`를 고른 뒤에는 해당 설정만 단독으로 clean run을 다시 실행하고, 그 결과만 extract 단계에 사용한다.
