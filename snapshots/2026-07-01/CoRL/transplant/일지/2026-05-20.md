## 💻 2. codex (00~03 재정리, MEP/HSP S1 로깅 축소, HSP preference 확인)

### 🔹 어떤 과정을 진행했는가
- **01 MEP S1은 MEP 6개만 학습하도록 정리함.**
  - 목표 S2 구조가 `MEP 6개 × init/mid/final = MEP 18개`이므로, 01에서 `mep1~mep12`를 학습하는 것은 불필요하다고 판단함.
  - `MEP_POPULATION_SIZE` 기본값을 `12 -> 6`으로 맞추고, `mep/s1/train.yml`도 `mep1~mep6`만 생성되도록 정리함.
  - 02 extract는 이미 기본적으로 `mep1~mep6`만 추출하므로, 01과 02의 정책 수가 일관되게 맞춰짐.

- **01 MEP S1 완디비 로깅을 핵심 3개 scalar만 남기는 방향으로 정리함.**
  - 유지:
    - `stage1_mep/train/mepX-value_loss`
    - `stage1_mep/train/mepX-policy_loss`
    - `stage1_mep/train/mepX-average_episode_rewards`
  - 제거/비활성화:
    - `dist_entropy`
    - `actor_grad_norm`
    - `critic_grad_norm`
    - `ratio`
    - `average_nlog_pop_act_prob`
    - `stage1_mep/env/*`, `stage1_mep/pool/*` 계열 raw scalar
  - 목적은 01 단계에서 정책별 loss/reward 추세만 빠르게 확인하고, 완디비 panel 폭발을 줄이는 것임.

- **03 HSP S1 train scalar도 핵심 3개만 남기는 방향으로 정리함.**
  - 유지:
    - `stage1_hsp/train/value_loss`
    - `stage1_hsp/train/policy_loss`
    - `stage1_hsp/train/average_episode_rewards`
  - HSP S1의 세부 event 행동 분석은 05 eval 이후나 별도 preference table로 보는 편이 더 적절하다고 정리함.

- **HSP preference에서 `w0`와 `w1`의 의미를 코드 기준으로 확인함.**
  - 원본 HSP repo의 HSP S1 스크립트는 `w0`에 random preference weight를 넣고, `w1`은 `0,0,...,0,1`로 둠.
  - transplant의 `03_train_hsp_s1_risky.sh`도 기본값 기준으로:
    - `HSP_W0 = r5, r5, ..., 1`
    - `HSP_W1 = 0, 0, ..., 1`
    으로 생성함.
  - 따라서 **preference 관점에서는 `w1`이 “거의”가 아니라 확실히 no-preference baseline**임.
  - 더 정확한 표현:
    ```text
    w1은 hidden event preference가 확실히 없다.
    w1의 hidden utility는 sparse reward만 본다.
    단, 전체 training reward에는 dense shaping term이 더해질 수 있으므로
    total reward 기준으로 완전한 sparse-only라고만 말하면 부정확하다.
    ```
  - `--random_index` 때문에 episode마다 물리적 agent 위치는 바뀔 수 있지만, preference vector 자체는 `w0`만 의미 있는 preference를 가짐.

- **00~04를 새로 돌리기 전, 기존 로컬 기록 삭제 범위를 정리함.**
  - 사용자는 완디비 run 삭제가 아니라 **로컬 기록만 삭제**하고 새로 돌리는 방향을 선택함.
  - 사용자는 Codex가 직접 실행하지 말고, 실행 코드를 제공해달라고 요청함.
  - 짧은 검증 기준은:
    - `NUM_ENV_STEPS=120000`
    - `SEED_MAX=2`
    - `MEP_POPULATION_SIZE=6`
    - `USE_WANDB=1`
    - 범위는 `00~04`
  - `00~04`로 잡은 이유는 03 HSP S1 학습 후 04 extract까지 해야 `policy_pool/risky_multipath/hsp/s1`이 새 결과로 갱신되기 때문임.

### 🔹 왜 그 과정이 필요한가
- HSP S2에서 실제로 쓰는 MEP partner는 `mep1~mep6`의 3 checkpoint이므로, 01에서 `mep7~mep12`를 학습하면 시간과 완디비 공간을 낭비한다.
- 01과 03은 학습 단계이므로 너무 많은 scalar를 올리기보다 loss/reward 중심으로 모니터링하는 편이 해석이 쉽다.
- HSP preference를 완디비 table로 정리할 경우, `w1`까지 event weight table로 펼치면 all-zero row가 많아져 화면만 지저분해진다.
- 따라서 HSP preference table을 만든다면 `hspX_w0` 중심으로 보고, `hspX_w1`은 `baseline/no-hidden-preference`로 요약하는 것이 적절하다.
- 기존 기록을 지우고 다시 시작할 때는 `results`와 `policy_pool`의 어떤 디렉터리를 지우는지 명확히 해야 이후 02/04 extract 결과가 꼬이지 않는다.

### 🔹 기존 환경인 HSP에서는 어떤 것을 사용하거나 수정했는가
- HSP 원본 repo의 HSP S1 스크립트와 env reward 계산을 확인함.
  - 원본 HSP S1 스크립트는 `w0`에 random weight를 주고 `w1`은 all-zero event weight + sparse weight 1로 둠.
  - 원본 HSP env도 `hidden_reward + reward_shaping_factor * dense_reward` 구조를 사용함.
- HSP 원본 코드는 수정하지 않음.
- HSP 원본 구조를 기준으로 transplant의 `w0/w1` 해석과 S1/S2 logging 목적을 맞춤.

### 🔹 기존 환경인 risky에서는 어떤 것을 사용했는가
- Risky `EVENT_TYPES`를 기준으로 `HSP_W0`, `HSP_W1` 길이를 생성함.
- `w0/w1` hidden utility는 Risky event vector에 대해 dot-product 되는 구조임을 확인함.
- Risky 환경 자체의 transition, event definition, reward source는 수정하지 않음.

### 🔹 왜 그 과정이 필요한가
- 최종 adaptive policy 평가에 쓰일 MEP baseline pool은 후속 HSP/adaptive 실험의 기준점이므로, full run 전에 HSP 논문/repo의 Stage 1 설정과 Risky 환경 설정이 정확히 반영되어야 한다.
- `01_train_mep_s1_risky.sh`만 실행하면 raw checkpoint가 `results`에 저장될 뿐이고, 최종 평가에서 바로 사용할 policy pool은 만들어지지 않는다.
- 따라서 01 학습 종료 후 반드시 `02_extract_mep_s1_risky.py`를 실행해 `policy_pool/risky_multipath/mep/s1`에 `18`개 MEP policy를 생성해야 함을 명확히 정리할 필요가 있었다.
- 초반 reward가 `-120` 근처인 것은 `TIME_COST=-0.3` 환경에서 정상적인 baseline이므로, 이를 학습 실패로 오해하지 않도록 해석 기준을 정리했다.

### 🔹 기존 환경인 HSP에서는 어떤 것을 사용하거나 수정했는가
- HSP 논문/repo의 Stage 1 MEP hyperparameter 구조를 기준으로 transplant MEP full 설정을 맞춤.
  - `num_env_steps=10M`
  - `episode_length=400`
  - `n_rollout_threads=100`
  - `reward_shaping_horizon=100M`
  - `ppo_epoch=15`
  - `num_mini_batch=1`
  - `entropy_coef=0.01`
  - `mep_entropy_alpha=0.01`
- HSP 원본 코드는 수정하지 않음.
- 단, Risky 환경에는 HSP 원본에 없는 `p_slip`, `time_cost`가 있으므로 transplant 쪽 공통 인자에 반영함.

### 🔹 기존 환경인 risky에서는 어떤 것을 사용했는가
- Risky layout은 `risky_multipath`를 사용함.
- Risky slip 설정으로 `P_SLIP=0.15`를 사용함.
- Risky time penalty 설정으로 `TIME_COST=-0.3`을 사용함.
- `neglect_boarders`는 HSP 원본과 맞추기 위해 켜지 않음.
- Risky reward/event 정의 자체는 수정하지 않음.
